# MCP 2026-07-28 标准研究

> 研究对象：`modelcontextprotocol/modelcontextprotocol` tag `2026-07-28`（tarball SHA-256 `7df4915b4a5cdc99...`）。<br>
> 结论：这是 2026 年的**重大不兼容修订**；官方 TypeScript SDK 1.32.2 稳定版仍以 `2025-11-25` 为最新稳定协议（`2026-07-28` 仅以 `DRAFT-2026-v1` 类型出现）。但 **Rust RMCP 3.8.0 已支持 2026-07-28 与 2025-11-25**，因此 Hisha 用 Rust RMCP 实现 MCP Gateway/Client/Server，TS 只做管理，不再自建协议层。

## 1. 版本时间线

| 版本 | 关键变化 |
| --- | --- |
| 2024-11-05 | 初始规范；HTTP+SSE 传输 |
| 2025-03-26 | Streamable HTTP 取代 HTTP+SSE；OAuth 授权 |
| 2025-06-18 | 结构化工具输出、elicitation 等 |
| 2025-11-25 | 当前 SDK 稳定目标；任务（tasks）实验、缓存提示等 |
| **2026-07-28** | **无状态化、移除 initialize/会话、server/discover、MRTR、subscriptions/listen、tasks 扩展、resultType、缓存字段** |
| draft | 下一代草案 |

## 2. 2026-07-28 的主要变更（逐条）

1. **移除协议级会话与 `Mcp-Session-Id`**：Streamable HTTP 不再有会话；`tools/list`、`resources/list`、`prompts/list` 不再随连接变化。跨调用状态由服务器显式 mint 的 handle 作为普通工具参数传递（SEP-2567）。
2. **无状态化**：移除 `initialize`/`notifications/initialized` 握手；每个请求在 `_meta` 携带 `io.modelcontextprotocol/protocolVersion`、`clientCapabilities`，可选 `clientInfo`；服务器在结果 `_meta` 返回 `serverInfo`；版本不匹配返回 `UnsupportedProtocolVersionError`（SEP-2575）。
3. **`server/discover`**：服务器必须实现，返回 supportedVersions/capabilities/identity；客户端可先探测，也可作为 STDIO 的向后兼容探测。
4. **`subscriptions/listen`**：替代 HTTP GET 与 `resources/subscribe`/`unsubscribe`；单选长连接 POST-response 流，按类型 opt-in（toolsListChanged、promptsListChanged、resourcesListChanged、resourceSubscriptions），服务器用 `io.modelcontextprotocol/subscriptionId` 标记通知。
5. **移除 `ping`、`logging/setLevel`、`notifications/roots/list_changed`**：日志级别改为每请求 `_meta` 的 `io.modelcontextprotocol/logLevel`。
6. **Tasks 移出核心**：成为官方扩展 `io.modelcontextprotocol/tasks`；用 `tasks/get` 轮询、`tasks/update` 输入，移除 `tasks/list`；服务器可主动返回 task handle（SEP-2663）。
7. **MRTR（Multi Round-Trip Requests）**：服务器不再主动发 `roots/list`/`sampling/createMessage`/`elicitation/create`；返回 `resultType: "input_required"` + `inputRequests`，客户端在重试原请求时带 `inputResponses`（SEP-2322）。
8. **`resultType` 必填**：普通结果 `complete`，MRTR 中间结果 `input_required`；旧服务器缺省按 `complete` 处理。
9. **移除 SSE 断线重放**：`Last-Event-ID`/event id 不再用于 redelivery；断流即丢失，客户端必须用新 request id 重发。
10. **缓存字段**：`tools/list`、`prompts/list`、`resources/list`、`resources/read`、`resources/templates/list` 返回 `ttlMs` + `cacheScope`（public/private）。
11. **HTTP 头**：POST 必须带 `Mcp-Method`、`Mcp-Name`；工具参数可映射自定义 header（`x-mcp-header`）。
12. **资源未找到错误码**：从 `-32002` 改为 `-32602`。
13. **OpenTelemetry**：文档化 `_meta` 的 `traceparent`/`tracestate`/`baggage` 传播。

## 3. 传输

### stdio

本地进程；JSON-RPC 走 stdin/stdout；适合 Local Runtime/桌面。认证通过环境变量（不应使用 OAuth 流程）。`server/discover` 可用于探测版本。

### Streamable HTTP

- 单一 HTTP endpoint，仅 POST；每个 JSON-RPC 请求独立 POST。
- 响应为单个 JSON 或请求作用域的 SSE 流；服务器到客户端的交互通过 MRTR 嵌入结果。
- 无 GET 流、无会话、无断线重放；长连接通知走 `subscriptions/listen`。
- 必须校验 `Origin`（防 DNS rebinding）；本地绑定 loopback；生产必须认证。
- 请求头 `Mcp-Method`/`Mcp-Name`；缓存字段遵循 `ttlMs`/`cacheScope`。

### legacy

2025-11-25 及更早的 Streamable HTTP（含 GET/会话/断线重放）与 HTTP+SSE 仍可能存在于客户端/服务器。Hisha 只在兼容层中支持，不作为新设计。

## 4. 授权

- 基于 OAuth 2.1 draft-13、RFC 6750、8414、7591、8707、9728、9207、CIMD、OIDC Discovery。
- MCP Server 是 OAuth 2.1 Resource Server；必须实现 RFC 9728 Protected Resource Metadata。
- 客户端必须支持 RFC 8414 与 OIDC Discovery 两种 AS 发现。
- Client ID Metadata Documents 优先；DCR（RFC 7591）已弃用但保留兼容。
- 不得把客户端 token 透传给上游 API（token passthrough 禁止）；每个上游使用自己的凭证。
- stdio 用环境变量凭证，不走 OAuth。

## 5. SDK 现状（关键）

**Rust RMCP 3.8.0**（crates.io，2026-10-26，Apache-2.0，MSRV 1.88）：
- `src/model.rs` 定义 `V_2026_07_28`、`V_2025_11_25` 与 `KNOWN_VERSIONS`。
- 支持 `server/discover`、MRTR、`resultType`、`subscriptions/listen`、tasks、Streamable HTTP/stdio、OAuth。
- 官方 Rust SDK（modelcontextprotocol/rust-sdk）；Hisha 可用它实现 Gateway/Client/Server，而不是自建协议层。
- LICENSE 仍处于 MIT→Apache 过渡；保留 NOTICE/法务复核。

**TypeScript SDK 1.32.2**：
- `dist/esm/types.js`：`LATEST_PROTOCOL_VERSION = '2025-11-25'`，支持到 2025-11-25。
- `dist/esm/spec.types.js`：`LATEST_PROTOCOL_VERSION = "DRAFT-2026-v1"`，类型在开发中，传输/服务器实现仍以 2025-11-25 为稳定路径。
- 因此 TS SDK 不作为 Hisha 的 MCP 主实现；TS Control Plane 只做注册/管理/审计查询。

**含义**：
1. Rust RMCP 负责协议/传输/认证；Hisha 加租户/策略/审批/注册表/审计。
2. TS Control Plane 不实现 MCP 协议；外部客户端由 Rust Gateway 处理。
3. 仍需 conformance 测试覆盖 2026-07-28 与 2025-11-25；RMCP 版本锁定。

## 6. Hisha 的设计决策

- **目标协议**：2026-07-28 为默认；2025-11-25/2025-06-18 为兼容。
- **协议实现**：Rust RMCP 3.8.0（官方 Rust SDK）；Hisha 只加租户/策略/审批/注册表/审计；TS 不实现协议。
- **MCP Gateway**：面向外部客户端的 Streamable HTTP 端点，OAuth 2.1 + 租户隔离；不做 token passthrough。
- **Local MCP Server**：stdio + 本地 capability token；不依赖云；支持 discover。
- **Tool/Resource/Prompt 注册**：由 Hisha Capability Registry 动态生成；每个工具有 JSON Schema、权限、风险级别、审批策略。
- **结果**：所有结果带 `resultType`；高风险写操作在 Hisha 侧要求审批，即使协议本身不强制。
- **可观测性**：`_meta` 传播 OTel trace context；Hisha 记录 tool call 审计。
- **缓存**：列表结果带 `ttlMs`/`cacheScope`；Hisha 对租户私有工具使用 `private`。
- **任务**：长任务通过 `io.modelcontextprotocol/tasks` 扩展或 Hisha 的 execution handle；不依赖旧的阻塞 `tasks/result`。

## 7. 风险

- 2026-07-28 与部分客户端生态不兼容；外部客户端可能只支持旧版。
- RMCP 版本/许可/规范跟进需要 conformance 测试与锁定。
- OAuth 发现/CIMD/DCR 的实现差异；企业 IdP 兼容性。
- 无会话后，服务器端限流/幂等/租户识别必须依赖 token + 请求级 handle，不能依赖连接状态。
- 缓存字段可能导致租户数据跨用户缓存；必须正确设置 `cacheScope`。
